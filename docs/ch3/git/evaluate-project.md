# 开源项目活跃度与贡献难度评估表
## 项目活跃度评估
- [ ]  最近提交、Issue 和 Review 是否持续发生 
##  任务难度
- [ ] CONTRIBUTING、许可证[^license]、行为准则和沟通渠道是否清楚  
- [ ] 任务是否有复现条件、影响范围和验收标准
- [ ] 是否需要特殊硬件、付费服务、部署权限或私有数据
- [ ] 新人是否能在课程周期内完成并获得可追踪证据[^evidence]
## 结论等级
- ??? note "合适(点击展开)"  
    项目活跃度高，任务难度部分的要点有至少三个成立。或项目活跃度低，但有明显的可修改的简单错误
- ??? note "需教师确认(点击展开)"  
    项目活跃度高，但需要特殊硬件、付费服务、部署权限或私有数据
- ??? note "不合适课程(点击展开)" 
    任务难度部分仅有一个成立或没有任一成立  

[^license]:规定他人使用开源代码权限的法律文件  
[^evidence]:如新手的PR记录
## 例子  
### 示例A: 
**假想项目:'desktop-pet'**  
- **活跃度**：最近一周有多次issue提出或PR  
- **任务**：要求增加清晰小人模型  
- **评估**：任务简单，仅需判断所需文件格式并搜集然后提交  
- **结论：合适**
### 示例B: 
**假想项目:'IoT-Gateway'**  
- **活跃度**：最近两个月内有多次issue提出或PR  
- **任务**：要求测试其网关的并发性能  
- **评估**：任务说明中指出，需要连接真实的树莓派 4B 设备或购买 AWS 实例进行压测。 
- **结论：需教师确认** 
### 示例C: 
**假想项目:'Fake-Legacy-CMS'**  
- **活跃度**：半年无提交，Issues 无人回复  
- **任务**：Issue里写着“系统太慢了，优化一下”  
- **评估**：无明确验收标准，且项目停滞 
- **结论：不合适课程**
